# 核心概念

Gatehouse 把“谁在申请”“访问哪个目标”“允许怎样访问”分别记录。部署时先理清这三件事，后续配置就不会把各种公钥混在一起。

## 三种连接身份

| 身份 | 用在哪里 | 认证材料 |
| --- | --- | --- |
| Gatehouse 普通用户 | 登录堡垒机受控菜单 | 客户端持有的接入私钥，对应用户登记的公钥 |
| 目标账号 | 堡垒机连接后端服务器 | 凭据库保存的目标私钥，对应后端账号的 `authorized_keys` |
| 临时账号 | 新终端或工具连接堡垒机 | 申请生成的 `ghp_` 用户名与随机密码 |

普通用户和临时账号都是应用身份，不是宿主机 Linux 用户。普通菜单不提供宿主机 shell。临时连接使用独立的账号密码，不需要把普通用户的接入私钥交给工具。

## 服务器、凭据与目标账号

**服务器**记录后端的地址、SSH 端口和已核验的主机公钥。**凭据**保存用于登录后端的私钥。**目标账号**把服务器、凭据与远端用户名关联起来，例如“生产服务器上的 deploy”。

授权和连接申请中使用的 `ACCOUNT_ID` 是目标账号的记录 ID，不是 `deploy` 这样的远端用户名。一个服务器可以关联多个目标账号。

主机公钥用于证明“连接的是预期的服务器”；用户公钥用于证明“来访者是谁”。Web TLS 证书则用于 HTTPS，它们是不同用途的身份材料。

## 临时连接申请

执行 `proxy create` 后提交用途说明。批准的申请绑定目标账号、模式、PTY、命令、文件目录或 TCP 端点，同时限制时间、来源、连接数、通道数和流量。

签发结果包含临时用户名、密码、入口地址、主机指纹与可复制命令。后续客户端仍连接**堡垒机地址**，服务端根据临时账号定位固定目标，再核验真实 SSH 请求。

`ttl` 是允许新连接认证的窗口；`duration` 是每条已建立连接的最长持续时间。二者都以秒为单位。超过连接次数、同时连接数、模式或其他约束会被拒绝；申请不是通用 SSH 通行证。

## Web 与 SSH 的关系

Web token 由已登录的普通菜单签发，120 秒内单次兑换。Web 会话依赖原菜单连接，空闲上限 15 分钟，绝对上限 2 小时。临时账号不能申请 Web token。

Web 的写操作还需要原菜单执行 `web confirm DIGEST` 返回的确认码。该确认绑定本次请求正文，修改字段后必须重新确认。可以打开 Web 页面，不代表拥有页面中所有对象的管理权限。

## 所有者与普通授权

首次初始化创建所有者，负责初始配置和授权。普通用户默认没有目标访问权限；应明确授予能力和资源，再按需要增加来源、时间和配额约束。

权限委派通过父授权向下收窄范围，不能扩大父授权的能力、资源或额度。撤销父授权会影响下级授权与相关连接。具体能力名称和示例见[权限与委派](permissions.md)。
